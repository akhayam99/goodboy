# Hosts

> **Read this when** you change what Goodboy does on GitHub, GitLab or Bitbucket, add a fourth host, or wonder where a host fact such as a merge method or a link shape comes from. **Not for** what an agent can ask a host through the bridge (`query-bridge.md`) or how a pull request page looks (`navigation.md`).

Every fact that differs per host lives in one table: `HOST_CAPABILITIES` in `packages/core/src/review-source/hostCapabilities.ts`. One row per host. The adapters (`githubReviewSource`, `gitlabReviewSource`, `bitbucketReviewSource` and their pull request ports) read the row. They do not carry their own copy of a merge method list, a url segment, a label or a noun.

| `commitSegment`        | The path piece that comes before a commit sha in a commit link                                                                                                                                                                                                                                                         |
| `identity`             | Where "who am I" comes from: the `gh` login, an access token, or an email with a token. The `gh` login runs only when no key is stored; a key that cannot be read stops the call with an error. A GitHub image in rendered Markdown needs a stored key; the `gh` login is not borrowed to load it, and the app says so |

## A merge carries the head the user reviewed

A workspace can mix hosts, a GitHub repository next to a GitLab or Bitbucket one. The Branch page then speaks the host of the repository on screen: the noun (`pull request` or `merge request`), the create flow, the checks and the review counts come from the shown mount, never from the mount chat writes to. `pullRequestViews` is keyed by session and mount for the same reason.

Creating a request is safe to repeat. `createPrForSession` reads `gh pr create`'s "already exists" answer and links the request it names; `createMrForSession` first asks GitLab for the open request of the source branch and links it instead of creating. Both return the number even when saving the link or the `pr_created` event failed, and say so in a warning notification (**Opened #14, but Goodboy could not save the link**); the refresh that follows finds the request by branch. Bitbucket creates nothing from Goodboy.

The base of a new request is the name of a branch on the host, never a remote tracking ref. A mount can store its base as `origin/main` (the ref the diff and history read), and `gh pr create --base origin/main` makes GitHub answer with a list of blank shas. `requestBaseBranchOf` (`features/integrations/shared/`) is the one place that turns the caller's base, the mount's base and the project's base into a name: it asks `git_remote_names` for the remotes the repository has and cuts a leading `<remote>/` or a `refs/remotes/<remote>/`, so `upstream/develop` becomes `develop` and `release/2026` stays whole. If the remotes cannot be read it falls back to `origin`. `createPrForSession` and `createMrForSession` both use it, and so does every caller of them (the Branch page form, the query bridge, the Scribe job). A new create path calls it too. `createPrForSession` pushes the branch before it asks `gh`, and `createPrFailureText` turns GitHub's refusal of a missing base, a missing head or an empty range into one sentence that says what to do (`Couldn't open the pull request: the branch isn't on GitHub yet. Push it and retry.`); any other refusal keeps the host line.

Every merge command takes `expectedHeadSha`, the head of the request as the user last read it. GitHub and GitLab refuse a moved head themselves. Bitbucket has no pin parameter, so `bitbucket_merge_pull_request` re-reads the pull request and compares `source.commit.hash` first: there is a short window between that read and the merge that the host does not close. Each refusal reaches the app as the error kind `stale_head` (Rust `StaleHead`, TS `PullRequestPortError` kind `stale_head`), whose message is `STALE_HEAD_MESSAGE`: refresh and review again. The store refreshes the request after a `stale_head` so the page shows the new head. A merge with no known head (a GitLab request read without `sha`) goes through unpinned, and so do merges the query bridge makes for an agent, because no one reviewed a head for them. The contract test in `pullRequestPortContract.test.ts` runs a moved head against every host.

## What a host failure looks like

Rust owns the failure taxonomy. `integrations/failure.rs` holds one set of kinds (`bad_credentials`, `denied`, `not_found`, `rate_limited`, `network`, `timeout`, `failed`) and one table from HTTP status to kind: 0 is `network`, 401 `bad_credentials`, 403 `denied`, 404 `not_found`, 408 `timeout`, 429 `rate_limited`, anything else `failed`. A provider error serialized with `impl_error_serialize!(Error, failure)` keeps its old `kind` and `message` and adds `failureKind`, `status`, `retryAfterSeconds` (only on a 429 that sent a whole-seconds `Retry-After`) and `detail`, the upstream text without Goodboy's prose. GitLab, Bitbucket, Jira and Linear send them. Their `failure()` method is an exhaustive match, so a new error variant does not compile until it says which kind it is. Caller input errors are `InvalidInput` and carry no failure kind. A 403 is never an authentication failure: Jira has `Forbidden` beside `Auth`.

The webview reads `CommandError.failure` (`hostFailureOf`). The GitLab and Bitbucket classifiers only pick the copy for a kind, and `pullRequestFailureKindOf` maps a kind to the `PullRequestFailureKind` the pull request page knows. They never read the status out of a message. An error without a `failureKind` reads as `failed`. Sentry, Slack and the `gh` stderr markers in `classifyGhFailure` still classify on their own.

## What an unreachable host looks like

Only a `network` or `timeout` failure means the host did not answer. A refused sign-in, a missing project or a rate limit means it did, and it ends an outage. `refreshMountRequest` takes the host of the adapter (GitLab and Bitbucket pass theirs) and reports each answer to `hostReachability`; an answer to a question asked before the last counted one is dropped. After three unreachable answers a silent refresh waits five minutes, the pace of `hostPollDelayMs`. A silent refresh of a mount that already holds an entry writes no pending state and writes the result only when it changed. GitHub goes through `gh`, whose failures are classified by `classifyGhFailure` and do not reach this state yet. The line under the top bar reads "GitLab unreachable since 10:42" with Retry, says it checks again every five minutes once it has backed off, and turns into "GitLab is reachable again" for four seconds when the host answers.

## What a request state looks like

`RequestState` in `integrations/request_state.rs` is `open`, `merged`, `closed`, `draft` or `unknown`. Each adapter maps its raw host string once, in an exhaustive match: GitLab `opened` is `draft` or `open`, `locked` is `open`, Bitbucket `OPEN`, `MERGED`, `DECLINED` and `SUPERSEDED`. A string nobody mapped is `unknown`, never a silent `open`. The raw string stays in `state` for what only the host knows, such as the GitLab queue (`locked`). `requestStateKind` in `packages/core` turns the state into the kind the app prints, and a test reads `request_state.rs` to keep the two lists equal.

## How the store keeps every host fresh

One sweep, `sweepRequests` (`store/slices/review-source/`), refreshes the request of every mount of every session on boot, on a branch change, when a token is set and every five minutes (`useGithubPolling`). For each mount it asks `mountRequestHostOf` which host the mount lives on: the GitLab or Bitbucket entry the mount already holds, else the project remote (`requestHostOfRemote`: Bitbucket by name, GitLab by the hosts the workspace connected or by name, GitHub by name), else GitHub. The GitLab and Bitbucket refreshers resolve a context only when the worktree remote names their own host, so a GitHub mount never gets a GitLab entry. `refreshMountRequests` sends the mount to `refreshSessionPr`, `refreshSessionMr` or `refreshSessionBitbucketPr`, each with `silent: true` and one retry. A host is asked only when it can answer: `gh` available for GitHub, a connected binding for GitLab and Bitbucket. A mount whose request merged or closed is skipped on every host, and the five-minute tick also skips a mount already read with no request.

Each host slice keeps one entry per mount (`mountGithub`, `mountGitlabMr`, `mountBitbucketPr`) with `fetchedAt`, `failedAt` and the request. `mountFetchFactsOf` reads them the same way for all three, and `sessionRequestFetchOf` folds the mounts of a session into one answer: `known`, `unknown` (nothing fetched yet) or `unreachable`, plus the host that answer is about. For GitLab and Bitbucket `unreachable` means exactly that `hostReachability` holds an outage for the host, so the board, the stage reason and the line under the top bar share one source; a refusal the host sent (a bad key, a missing project) is not an outage. For GitHub, which `hostReachability` does not cover yet, it means the newest attempt failed. The stage reason (`checking GitLab`, `GitLab unreachable`, `no MR yet`) and the board's cloud icon word it from that host, never from `gh` state.

For the open session the same pass then reads the review threads of that mount: `refreshMountThreads` sends the mount to `refreshSessionPrDetail` (GitHub), `refreshGitlabReviewThreads` or `refreshBitbucketReviewThreads`, and the two latter share one step, `refreshSourceThreads`, where the host only picks the transport. Threads are skipped while younger than 30 seconds, named by mount and request (`reviewSourceThreads`), and the reads of all hosts share one bound of `REVIEW_REFRESH_CONCURRENCY` (`boundedThreadRead`), and a request that a newer one replaced, or whose mount revision moved, stops before every write of `syncSourceThreads` (`isCurrent`), not only before the comments cache. Every helper under it that awaits and then writes (`saveResolveThread`, the `loadResolve*Into` loaders, `reconcileHandReplies`, `syncSourceSnapshots`) takes the same optional `isCurrent` and checks it after its last await, so a stale request writes nothing from any depth. `reconcileResolveLane` is the exception: it is a step over database state, not over the fetched response, so it takes no `isCurrent`, runs whole, and runs one at a time per session through the lane queue in `resolve/index.ts`, reading the database when it starts. Its compensation defers a taken-up item only while that item is still unanswered, so a newer refusal stays. `resyncSession` reports only the thread errors of the requests the mounts show now (`currentThreadKeysOf`). A host that fails keeps its last threads; a quiet sweep hides the error once threads exist. `resyncSession` calls `sweepRequests({ sessionId, isForced: true })`, so Refresh and the tick run one code path, forced for that session's mounts only.

| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |

`src-tauri/gh-allowlist.json` is the one list of `gh` command shapes. `gh_allowlist.rs` reads it for `gh_run` and for the query bridge (`query_bridge/github.rs`), which still builds its own `gh pr` commands for agents with its own `--limit` and field list and now has each one checked against that list. `gh_run` also refuses `--hostname`, `--input`, `GH_HOST`, a GraphQL mutation that is not listed by name, and a working directory that is not a registered project or session worktree. A new `gh` call in `packages/core` needs a shape in the file; `gh-allowlist-parity.test.ts` runs the core callers against it.

## Find the request for a branch

The same question gets the same answer on every host: look at every state, prefer an open request over a merged or closed one, and among requests of the same kind take the one updated last. GitHub asks `gh pr list --head <branch> --state all` and picks in `resolvePrForBranch`. GitLab asks `state=all`, newest first, 20 at a time and picks with `pick_request_for_branch`. Bitbucket asks for the four states (`OPEN`, `MERGED`, `DECLINED`, `SUPERSEDED`) sorted by `-updated_on` and picks with `first_matching_branch`. Each pick has a test, so a lost link to a request that merged can be rebuilt on all three hosts.

## What keeps the table honest

- The review source contract (`packages/core/src/review-source/__tests__/reviewSourceContract.test.ts`) walks every row. A host with a fake source but no row fails, and so does a row with no fake.
- `hostCapabilities.test.ts` in the same folder checks each row against the capability flags, the labels, the url shapes and the merge method lists.
- The same test reads `apps/desktop/src-tauri/src/query_bridge/protocol.rs` and checks the bridge catalog against the row: every verb the row names must exist with the right access, a denied capability must have no verb, and the merge verb must take the parameter the row names.
- `packages/core/src/hostile-input.test.ts` and `hostile-input.perf.test.ts` run every exported parse, slug, sanitize, normalize and strip helper in `packages/core/src` on a hundred thousand characters of hostile input.

## Where a stored secret may be sent

The webview never picks the host a stored secret travels to. The GitLab host, the Jira site and email and the Bitbucket workspace slug and email still arrive as command arguments, but `integration_credentials::require_bound` compares each one with the config of the binding (`host`, `siteUrl`, `email`, `workspaceSlug`) before the token is read. A value that differs, or a binding with no config, fails with `unbound_value` and the request is never sent. The comparison ignores case, surrounding spaces and a trailing slash. Only the `*_validate_connection` and `jira_list_projects` commands take an explicit host, because they run before a binding exists and carry the typed secret with them. `load_tool_image` applies the same check for Jira, so the image host it trusts is the bound site.

`secret_set` and `secret_delete` accept only `provider_credential.<id>`, where the id is 1 to 64 letters, digits or dashes. Every other keychain slot (integration credentials, legacy slots) is written by Rust alone.

## Cloning from a host

The Workspace step of setup clones through `repo_clone.rs`, the one clone path in the app. It knows three hosts by domain (`github.com`, `gitlab.com`, `bitbucket.org`) and accepts `https://`, `git@` and `ssh://git@` addresses with an owner and a name; GitLab also takes subgroups. Any other address, a `/tree/` link or a leading dash is refused as `unknown_source` before a process starts.

`clone_probe` asks before it clones. It runs `git ls-remote` with prompts and askpass off, without `--exit-code`, so a reachable repository with no refs counts as reachable; a reachable repository clones with plain git, which covers a public one. When that fails and the cause is not the network, the probe reads the login each host already has: `gh auth status` for GitHub, `glab auth status` for GitLab, and `git credential fill` for Bitbucket, which counts only when the helper returns a password. GitHub and GitLab then clone through `gh repo clone` or `glab repo clone`, so the CLI's own login is used. Every probe and clone command names the validated host and never a bare `owner/name` that a CLI default host could resolve elsewhere: git gets the normalized remote of that domain (an `ssh://` or `git@` address is rebuilt from the validated domain, `www.` dropped), and the CLIs get the full `https://<domain>/<path>.git` URL plus `GH_HOST` or `GITLAB_HOST` set to the domain. Every probe and clone process runs with `LC_ALL=C` and `LANGUAGE` removed, so git, `gh` and `glab` print English whatever the system language, and the phase and failure readers never meet a translated line. No login ends in `auth_refused`, and the app answers with one line naming the command to run and the Tools step. Bitbucket has no CLI route: a refused clone there means the credential helper holds nothing usable.

`clone_repository` takes a request id, streams `clone-progress` events and stops on `clone_cancel`. It accepts only a destination that does not exist: an existing folder, empty or not, a file or a symlink (even a dangling one) is refused (`destination_not_empty`, or `destination_not_a_folder` for a file) and never touched, and `clone_free_destination` returns the next free `-2`, `-3` name. Git never writes to the destination. The request creates a hidden staging folder with an atomic `create_dir` in the canonical parent, named `.<name>.clone-<request id>`, so no other request or person owns it, and clones into it. The request records the staging folder's identity (device and inode from `symlink_metadata`) and the canonical parent path at creation. Before any removal and before the final rename it re-canonicalizes the parent and re-reads the identity; on a mismatch (a replaced ancestor, a swapped folder, a symlink at the top) nothing is deleted or moved, the folder is left where it is, a warning is logged and a publish answers `failed`. The check runs just before the call, so a swap inside that window is still possible; it needs write access to the parent. Cleanup, child deregistration and the admission entry are released by a drop guard, so a panic or an error unwinds through them too, and a refused reader thread spawn is an `io` error, not a panic. Progress events carry only a typed phase (`Enumerating objects`, `Counting objects`, `Compressing objects`, `Receiving objects`, `Resolving deltas`, `Updating files`, or the generic `Working`) and a percent, never git's own text, so a line holding a credential cannot reach a window. The answer carries the path the clone was published to (the canonical parent plus the name), not the string the webview sent. On success the staging folder is moved to the destination with an exclusive rename (`renamex_np` with the exclusive flag on macOS, `renameat2` with the no-replace flag on Linux, in `proc/rename.rs`); a destination created in the meantime is never replaced or emptied: the staging folder is removed and the answer is `destination_not_empty` with a free name offered. A cancel is remembered by request id, so one that arrives before admission or before the child starts is honoured and the clone never runs; at most 32 markers are kept, the oldest dropped, and the webview sends a cancel only for a request it has invoked. Shutdown first closes admission under the same lock admission takes, then kills the children and removes the staging folders, so a `clone_repository` that arrives after is refused as cancelled; `db_wipe` reopens admission and bumps an admission generation: a call records the generation when it is invoked and is refused as cancelled when it changed, so a call queued before the shutdown never starts after the wipe. The child carries a spawn tag like the other children. The webview drops an answer whose token is no longer current, rechecks it after every await, locks the host, source and destination fields while a request is in flight, and leaving the step cancels a running clone.

## Adding a host

1. Add the host to `PullRequestHost` in `packages/types`. The row table stops compiling until it has a row.
2. Add its row, then its adapters, reading the row for every fact in the table above.
3. Add its fake to the review source contract. The contract fails until the fake and the row agree.
4. Add its bridge verbs in `protocol.rs` and name them in `bridgeVerbs`. The parity test fails until the catalog and the row agree.
5. Fill its column of the table above with the vendor page each field comes from.
6. Add its store step: a `refreshSession<Host>` that refreshes one mount through `refreshMountRequest`, one arm in `refreshMountRequests` (`store/slices/review-source/`), one entry reader in `mountFetchFactsOf`, one branch in `requestHostOfRemote` and, for review threads, one arm in `refreshMountThreads` that lists the comments through `refreshSourceThreads`. The sweep, the stage reason and the board signal read those, so nothing else in the store names the host.
