# Custom window events

> **Read this when** dispatching or listening for custom window events in apps/desktop. **Not for** events between app windows, which go through Tauri `emit`/`listen` (see Cross-window events below).

Every event on this page is a browser CustomEvent sent via `window.dispatchEvent()` and received via `window.addEventListener()` or a picker's `openEvent` prop. Payloads are the `detail` field. Window events are the cross-feature entry: a feature asks the app shell to open a studio or a surface without importing it.

## Request events

A row, a menu or a tour step asks the surface that owns an object to act (select, rename, edit, open a popover). The asker sends the event with `dispatchAfterNavigation` (it waits for the place to render) or from a `request*` helper; the owner listens in the file named below. A name that ends in `:<id>` carries the id of the session, project, tree or mount it is for, so one open surface answers only its own. A cancelable event reports `defaultPrevented` to the asker, which then knows an owner handled it.

## Cross-window events

Events between app windows use Tauri `emit`/`listen`, not the window bus. `features/workspace/window.ts` owns `goodboy:presence`, `goodboy:presence-request` and `goodboy:window-closing` (which workspace each window shows). `features/review/prWriteBus.ts` owns `goodboy:pr-write`, which claims and releases a pull request write so two windows never push the same PR at once. `features/auto/bridge/autoBridgeProtocol.ts` owns the Auto bridge: `goodboy:auto-request` and `goodboy:auto-response` carry a detached window's Auto calls to the main window, and `goodboy:auto-artifacts-changed` with `{ sessionId }` tells detached windows that an Auto admission or revise changed that session's plans, so `followArtifactAnnouncements` reloads them when the window shows the session. `shared/lib/dataChanged/` owns `goodboy:data-changed`, the one event for "a fact other windows show was written": after a committed write the writing window sends `{ kind, ..., origin }` (a random id of that window), and every other window reads that fact again and shows it (a window drops the echo of its own origin). `kind: 'setting'` with the `key` is the first user: `saveSetting` announces after the database write and the store change, and `listenSettingChanges` (mounted in `App.tsx`) calls `loadSetting` for that key, so a setting saved in one window shows in the others without a reload. A new shared fact adds a `kind` there, never a channel of its own. `shared/lib/attentionChannel/` owns `goodboy:attention`, the one exception because it carries a value instead of asking for a read: after its needs-you count changes, and every 30 seconds, a window sends `{ workspaceId, count, tone, reasonWords, origin }` for the workspace it shows, a window drops the echo of its own origin, and `useAttentionSync` (mounted by `AwayAlertsBridge`) keeps the reports of the other windows in `attentionFromWindows`. A report counts only for a workspace some window shows (`windowPresence`); for any other workspace the sidebar slice uses `attentionFromDatabase`, read from the `workspaces_attention` command, which counts the saved facts. Surfaces read the two through `useWorkspaceAttentionEntry` and `useAttentionElsewhere`, so a number is computed by `attentionByWorkspaceOf` once. `src-tauri/src/app_menu.rs` emits one event, `goodboy://menu` with `{ id }`, to the focused window only, when you choose any item of the macOS menu bar; `useMenuCommands` listens on its own webview window and replays the registry shortcut or runs the menu action of that id (`runMenuCommand`). There is one listener and no per-item event, so a new menu item never adds an event.

Turn output is one such event. Rust emits every `turn_event` (and every `chat_event`) to all windows with `AppHandle::emit`, never `emit_to` the owning window, because a detached window and a second window read the same session. Each window installs one listener per event name, in `features/chat/createRunEventRouter.ts`, and routes an envelope to the handler of its `runId`; the listener is removed when the last run leaves and installed again for the next one. `runTurn` and `attachTurn` (`features/chat/turn.ts`) subscribe to the `turn_event` router, and `streamChatTurn` to the `chat_event` router. A consumer that stops reading a stream must close it (`return()` on the iterator), or its handler keeps the listener alive. Eight or thirty-two streaming runs cost one listener call per envelope, which `STREAM_BUDGETS` pins (see [testing.md](testing.md) → No stopwatch in the gate).

Terminal, script and provider lifecycle output follow the same rule: `terminal-output` and `terminal-exit`, `script-output` and `script-exit`, `provider-lifecycle-output` and `provider-lifecycle-exit` each have one listener per window, installed by `createOutputStream` in `shared/lib/`, and every reader of a stream (a terminal panel, a run action, a replay) subscribes to it instead of calling `listen` itself. A new output stream is one more `createOutputStream` call. `shared/lib/createOutputStream.test.ts` pins one listener per event kind and an exit delivered once to each subscriber; `features/providers/provider-lifecycle.stream.test.ts` pins it for the three readers of the lifecycle stream.

## Events from Rust

Rust sends these to the webview with `AppHandle::emit`. A rename in Rust compiles and then fails silently in the webview, so `scripts/check-event-names.mjs` (part of `pnpm check:doc-refs`) compares them: every name below must be emitted in `src-tauri/src`, named by a frontend file, and listed here, and every name the frontend listens to must be emitted by Rust or by the frontend. The wire names keep three styles for now (`snake_case`, `kebab-case`, `scheme://path`); a new event uses `kebab-case`, and a rename lands in Rust and in the frontend in one commit so the check stays green.

## Git and request state is not on the bus

No window event announces a push, a new pull request or a branch switch. The
store action that changes git or request state refreshes the mount itself
(`refreshSessionPr`, forced, for that mount), and the Overview row reads the
store, so it updates without a listener. Changes made outside the app are
picked up by `recheckSessionMounts` on turn end and on window focus, and by the
header's Refresh. [mounts.md](mounts.md) lists every trigger. Do not add a
window event for this: a feature that wants fresh request state calls the store
action.

## Polling

A hook that reads on a timer calls `usePoll` (`shared/lib/usePoll/`), never `setInterval`. The gate is one rule for all of them: no tick runs while the window is hidden, a window that becomes visible reads once at once, and a `focused` gate also waits for window focus. The hooks on it are `useTerminalLedger`, `useTerminalPorts`, `useAutoTrees` (one shared poll per session, in `sharedPoll`), `useMonitorPolling` (shared by the monitor page, the ports row and `useScriptLive`), `useMonitoringSignalRefresh`, `useGithubPolling`, `useProjectGitStatuses`, `useRepoDivergenceCheck` and `useRebaseConflictFiles`. `usePoll.test` pins the pause on a hidden window, the read on return, the focus gate and the cleanup; `useTerminalLedger` pins it for a real poller. Still on a hand-made timer: the updater check (its own focus rule), the run watchdog, the window heartbeat, the PR write and worktree writer bridges, and the store-side timers of the git status cache, the resolve heartbeat and the Auto runtime.

## Adding an event

Event names follow the pattern `goodboy:verb-noun` (e.g., `goodboy:open-plan-studio`, `goodboy:reveal-chat`). Every event must be dispatched and listened in the same pull request, and its row lands here in the same commit; a listener without a dispatch is unreachable code. Payloads should stay minimal: pass only the ids and enums needed to route or initialize a feature, never entire objects. If an event grows past three fields, reconsider whether routing logic belongs in a store method instead.
