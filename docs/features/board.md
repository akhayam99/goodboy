# The board

The Board shows every session of a workspace in one of two layouts. **Queue** lists what waits on you, every agent at work and what is ready to merge. **Stages** puts the sessions in lanes by stage, so you see where each task stands. **Queue | Stages** sits in the Board head. The Board opens on Queue from the places rail and in a new window; Back returns the layout it had, and a reload keeps it. Sessions in the top bar lists the same sessions, so the page stays a board. Open a session and come back: the board is as you left it, with the same scroll and the same cards selected.

### Queue

Act on what waits without opening each session. Three bands sit on one screen.

- **Needs you** is a pile of moves, the oldest wait first. The focused move is a card with the one filled button; the others are rows. Answer a question with a choice or a line of text on the spot. The recommended answer is the filled choice. A typed answer stays while you look at another move. A permission, a plan or a question that takes several choices opens its page. **Not now** puts a move off with Undo, and **Show 1 hidden** brings back the moves put off in this workspace. With nothing left it says "Nothing waits on you."
- **Running** has one row per agent of every session, under its session: the agent, what it is doing, the project and how long it has run. The phrase changes every few seconds, never every second. Click a row or press Space to peek: the two steps before the current one and a field to message the agent, without opening the session.
- **Ready to merge** lists the pull requests approved with green checks, with no count beside the title. With none it says "Nothing to merge". An approved pull request with green checks waits here, not in Needs you. The rows come in a proposed order, with the reason under the first one: the smallest change first, and a branch before the one that builds on it.

**The merge train.** Merge several pull requests, across sessions and repositories, with one gesture.

- Tick the rows to merge. **Merge 2 in order** merges them one at a time, in the order shown. Its tooltip names the method: squash and merge.
- Before each merge Goodboy reads the pull request again. When an earlier one landed in the same repository, it first updates the next branch on main in its worktree and waits for its checks.
- A strip takes the head of the band, one line: "Merging 1 of 2 · #76 notify-relay", then "Updating #305 on main · checks running", then "Merged 2 of 2".
- **Stop after this one** lets the pull request in flight finish and stops there.
- The train stops at the first pull request it cannot merge and says why. A conflict goes to the Lead, which resolves the rebase; the train never resolves it alone.
- Nothing merges without your gesture: the train starts from the button or **M** and stops when you say so.

**Merge when green**, in the branch page menu while checks run, hands the merge to GitHub: it merges the reviewed head once every check passes. **Cancel auto-merge** takes it back.

An answer or a message waits ten seconds before it goes out. The toast offers **Undo**, and **⌘Z** outside a field does the same, so the agent never sees an answer you took back, and the text goes back in its field. Meanwhile the agent's row says "Answer queued". If the question was answered elsewhere first, the toast says so and nothing is sent. If the answer was saved but did not reach the agent, an error says so and opens the agent.

The keyboard works one band at a time. **F6** passes to the next band. **J**, **K** and the arrows move inside it. In Needs you, **Enter** is the filled button, **1** and **2** pick a choice, **→** opens the session with the move on top and **S** is Not now. In Running, Space opens the peek, **Esc** closes it and **→** opens the agent. In Ready to merge, **→** opens the pull request, Space ticks a row and **M** merges the ticked rows in order. Letters type as usual in a field.

### Stage board

See where each task stands without moving cards around. Six lanes, **Building**, **Running**, **Needs you**, **In review**, **Done** and **Archived**, always sit in that order, and each session sits in the lane that matches what is happening in it. A session waiting on your answer sits in **Needs you**, and so does one with a run that stopped, paused at its limit or waits for you to continue, an Auto agent that needs your OK, or a Slack reply that waits for your approval. The lane lists the longest wait first, and its tooltip teaches **⌥⌘↓**, the key to the next session that needs you. When nothing needs you the key says so in the top bar for two seconds, and when the open session is the only one it says that instead. The **Board** title sits on the same header row, at the same height, as every other page. While the page loads it shows empty lanes, until it knows what needs you in every session, so a card never changes lane after it appears. If that read fails, one line says so above the lanes, with **Retry**. With no session yet, **No sessions yet** sits under the title at its left edge. It says a session holds one goal, its agents and, for code, a branch. It draws the five lanes muted with one sentence each. The only **New session** button sits in the first lane.

### Done and Archived lanes

Finished work stays in view. In Sessions, in the top bar, finished sessions sit in a **Done** group after the others, so a merged session is one click from reopening. A session that never opens a pull request reaches **Done** too: an answer from a read-only agent, a report, a plan, or a finished edit in a folder with no branch reads **Done** with the reason "answered", "report ready", "plan ready" or "finished" in the hover card, once its reply is read and nothing is running or open; writing again brings it back. A session whose pull request merged or closed also leaves the live groups of Sessions at once, unless you wrote after the merge. The **Done** lane header carries a **⋯** menu with **Archive all in Done** and **Archive done older than 7 days** (by the session's last activity), each archiving at once with **Undo**, or asking first when an agent there is still live, like the card menu. **Done** and **Archived** are lanes like the others, and **Restore** on an archived card puts the session back where it belongs. On a narrow window the two share the last lane.

### Session card

Read a task at a glance: its title on two lines, its project in gray, and one signal at the right. The signal is the first that applies. A card in **Needs you** says why in words, the winning reason of the session registry: "Plan v3 needs approval", "2 questions for you", "Changes requested", "Approved, ready to merge", "An agent failed"; the list rows show the same words. When a run waits, the card names it on its own line, "Run Stop retried webhooks", with "+1" when a second run waits too, and the signal says why, such as "Plan is ready". Its round button then says what it does: **Review plan**, **Answer the Lead** or **Open run**, and opens that run in its session. In the other lanes it is a failed check or an open question, then the pull request in its state color (click it to open the pull request), or a running dot with the number of agents at work (the number shows from two on). While an agent works, a line says what it does, in the words of the session's Now: "Running pnpm test in payments-api". An agent with no project of its own names none. The line changes at most every 5 seconds, catches up within 15 and never moves; the hover card, the Now chip and Sessions say the same line. Age, linked issues, agent count, cost, the pin and draft review comments wait in the card that opens when you rest the pointer on it. When the signal already names the action that waits on you, such as "1 question for you", the signal itself is the button. No second icon shows. A card in **Needs you** with no action of its own works the same way and goes where the reason is cleared, like the top bar chip. A waiting run, **Continue** or a skip keeps its round button; the hover card also opens when the title takes keyboard focus; the rest of the session's verbs are in the card's right-click menu, among them **Mark as unread** and **Mark as read**. A thin colored line at the card's left edge tells its stage at a glance: gray while building, cyan and breathing while running, amber when it needs you, green in review, purple when done, and gray again once archived.

### Bulk select

Tidy many sessions at once. A card has no checkbox: **Shift** click picks a range, **Option** click adds or removes one card, a lasso with Option held picks the cards it crosses, **Shift+Enter** and **Alt+Enter** do the same from the keyboard, **Select** in a card's right click menu picks it, and **⌘A** picks them all. Then **Archive**, **Restore** or **Delete** them from the bar at the bottom. Archive asks once for all of them only when agents are still live, **Stop 2 agents and archive**, and stops them first; with nothing live it archives at once. Delete asks first. Archive and Restore can be undone, and when some sessions could not be archived the bar names them with **Retry**.

**↑** and **↓** move between the cards of a lane. With **Shift** they extend the pick one card at a time.

**Rename** in the same menu edits the title on the card. **Enter** saves once the write lands and **Esc** leaves the name as it was. When the write fails the card keeps its old name. The field stays open, says why, and offers **Retry**.

## Under the hood

This part is for contributors and agents who change the feature.

- Done lane menu: `DoneLaneMenu`, the `doneLane` object kind and `doneLaneArchivesOf` give the **Archive all in Done** and **Archive done older than 7 days** actions.
- Lane window: `StageColumn` draws 50 cards of the `done` and `archived` lanes (`LANE_WINDOW`); selection reads the whole list, so Select all keeps selecting every session. `loadArchivedSessions({ workspaceId, isForced })` serves its cache, joins an in-flight read and re-reads only when forced on window focus (`useArchivedSessionsLoad`). A read that overlapped an archive, restore or delete is dropped (`archivedCacheVersion`), so the action's cache write is never overwritten by the older read.
- Card keys: `useBoardArrowKeys` walks the `[data-select-id]` cards of the lane (`role="group"`) the key came from and extends through `BoardSelection.onToggle`.
- Card rename: `CardRenameField` draws `TitleField` (`density="row"`) over `useSessionTitleRename`. `renameTask` writes first. A failure keeps the old title, leaves the field open and shows `RenameStatus` with Retry.
- Main region: `App` gives the board (`WorkspaceBoard`, which reads its own sessions), the session frame and the draft to one `PaneSwap`. The layer that leaves stays mounted, inert, for 120 ms while the new one is live, then sits under `Activity`, so the board comes back with the same scroll and selected cards and no new read. `PaneSwap` keeps each scroller's offset, because a hidden layer is `display: none`.
- Card motion: `StageColumn` draws its cards through `useListMotion` and `ListItemMotion` (`packages/ui`). An arrival fades in with a 4px rise while its height opens over 200 ms, a leaver fades out over 120 ms and then collapses over 200 ms. A change of more than 20 cards, a change of the view prefs or project filter (`motionResetKey`) and reduced motion update in place. A card that changes lane with fewer than 12 cards on the board slides from its old place to its new one over 200 ms (`useLaneTravel`, a FLIP on `data-select-id`); it skips the fade in the lane it leaves and the one it enters, and travels only when both places are inside the board. At 12 cards or more, after a reset and with reduced motion it enters the new lane as before. The slide is clipped by the destination lane.
- Load gate: `setCurrentWorkspace` sets `boardReady` with the rows, never the PR sweep; `StageBoardCard` reserves the signal width (`card-signal-reserve`).
- Facts before the board: `loadWorkspaceFacts` reads the open questions and the Not now choices of every session, one query each. It reads the trees that are not at rest in one query (`listAutoTreesToRecover`), and full views only of the sessions with an Auto agent that hold one. All of it lands with `boardReady`, so no card moves after the first paint. Each fact keeps its own failure: a bad tree drops only that session's views. A failed read sets `workspaceFactsError`, and `BoardFactsFrame` shows it above the lanes with **Retry** (`retryWorkspaceFacts`).
- Card signal: `boardSignalOf` reads `attentionWordsOf`, so a new reason needs no second table.
- Card action in **Needs you**: `attentionPlace` is the place the top bar chip opens.
- Live line: `useFleetPhrase` reads `live_work` for every session in one call that all its readers share. A `work-changed` event or the poll (`FLEET_EVERY_MS`, 15 s) asks for a read while the window shows. `fleetPhraseOf` keeps the newest run's phrase. A phrase stays `FLEET_MIN_MS` (5 s) after it changed, and only the newest waiting one follows. A failed read keeps the last line, and a late answer is dropped. `StageBoardCard`, `SessionHoverCardBody`, the Now chip rows and `SessionsRow` read it.
- Waiting run: `waitingRunOf` names the run `attentionPlace` opens for the same reason, and `leadWaitWordsOf` gives a Lead its words and its button.
- Layout: `useBoardPage` keeps the layout and the focused move in the history entry (`PLACE_ROWS.boardLayout`, `PLACE_ROWS.boardMove`), so Back and a reload find them and a new entry starts on Queue. It writes only while the entry is the Board. `BoardLayoutSwitch` draws the control; `StageBoard` swaps `QueueBoard` and `BoardLanes`.
- Needs you count: `needsYouOf` counts the sessions with `attentionCountOf`, the count the places rail uses, and turns each loud reason into moves, one per open question. `pr-approved` stays out and lands in `readyToMergeOf`. It also needs `requestChecksOf` to read `success` (`readyToMergeOf.test.ts`). A question with `selectMode: 'many'` is a page move. Tested in `needsYouOf.test.ts`.
- Answer and message: `useQueueActions` queues them in `useQueueSends` for `UNDO_WINDOW_MS` and registers an `undoable` operation, so the toast and ⌘Z cancel the timer. At the end the question is read again and an answered one is skipped; the move stays aside until the send settles. A delivery failure (`OpenQuestionDeliveryError`) is reported with an `open-agent` action. Undo puts the text back in `drafts` or `answerDrafts` unless a newer draft is there. The first queued send registers one `pagehide` listener for the window, so leaving sends what waits even after the Queue unmounted. Tested in `useQueueSends/index.test.ts`, `useQueueActions/index.test.tsx` and `queue.rows.tsx`.
- Running: `useFleetWork` reads `live_work` for every session at most every ten seconds (`FLEET_EVERY_MS`). A `work-changed` event outside the view is ignored. A burst inside it waits for the interval. Retry reads at once and a late older read is dropped (`useFleetWork/index.test.tsx`). `earlierStepsOf` keeps the two steps before the current one for the peek.
- Merge order: `mergeOrderOf` proposes the order and its reason from `readyCarsOf`. It reads the mount, the base branch and the file count of a cached view. `useMergeTrain` holds the ticked rows.
- Merge train: `startMergeTrain` keeps one `mergeTrain` in the store, so the strip survives leaving the Queue. A second start while one runs answers `busy`. The train lives in the window that started it.
- Train engine: `mergeInOrder` serves the train and `mergeSeriesInOrder`. It reads each pull request before it merges and rebases the next branch with `rebaseBranch` when its repository moved. It polls the checks every 20 seconds for at most 45 minutes (`MERGE_WAIT`). A conflict goes to `resolveRebaseWithAuto`. Each stop has a test in `mergeInOrder.test.ts`, and `trainLineOf` gives the strip its line.
- Merge when green: `pullRequest.mergeWhenGreen` calls the port's `mergeWhenGreen`, `gh pr merge --auto` with the method and `--match-head-commit`, gated by `canMergeWhenGreen` (GitHub only). Tested in `pullRequest.mergeWhenGreen.test.ts` and `prQueued.test.ts`.
- Keys: `queueKeyOf` maps a key and the active band to one command (`queueKeyOf.test.ts`). `queueLandingOf` sends a question, a permission or a plan to the session overview and the rest to `attentionPlace`.
